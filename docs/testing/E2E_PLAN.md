# E2E 테스트 계획서 — 이희재의 맛 연구소 스튜디오

- 작성: 2026-11-12 · 대상: `apps/studio` (서버 + 화면) · 실행 도구: Playwright Test
- 목적: 최종 사용자(휴대폰 웹)가 실제로 누르는 순서대로 **처음부터 게시 기록까지** 끊김 없이 되는지, 그리고 AGENTS.md의 6가지 원칙과 보안 장치가 **화면을 거쳐서도** 지켜지는지 자동으로 확인한다.
- 단위 시험(Vitest 418개)은 함수·API 하나하나를 본다. E2E는 그 사이의 "이음매"(화면 ↔ 서버 ↔ 제작 파이프라인 ↔ 파일)를 본다.

## 1. 범위

| 넣는 것 | 빼는 것 (이유) |
| --- | --- |
| 로그인·첫 계정·계정 추가·비밀번호 재설정·연구자 계정 | 실제 인스타그램 게시 (외부 계정·사용자 승인 필요 → 가짜 Meta 서버) |
| 레시피 입력(직접·사진 읽기) → 주제 → 후보 5개 → 영상 → 블로그 → 검수·승인 → 내보내기 → 게시 기록 | 실제 Claude API 호출 (유료 → 가짜 Claude, 실제 1회 확인은 수동 단계) |
| 제작 파이프라인 실제 코드(`runRender`: 품질 검사 기록·재렌더·카드·표지) | 실제 3D 렌더 (CI에서 30분 이상 → 가짜 렌더러. 실제 렌더는 3단계에서 따로) |
| 원칙 1~4의 화면 경로, 승인·버전 묶임, 중복 게시 확인 | 실제 GPU 목소리 (클라우드 비용 → 목소리 없음 모드) |
| 보안: 미디어 허용 목록, 점 인코딩 우회, HTML 업로드, 다른 사이트 요청, 로그인 없는 접근 | |
| 휴대폰 화면 품질: 가로 넘침, 입력칸 16px(아이폰 확대 방지), 화면 오류(pageerror) | |
| 배포 뒤 실제 서버 점검(읽기만): 살아 있음, 로그인 화면, 보호된 주소 | |

## 2. 실행 단계

| 단계 | 무엇 | 언제 | 시간 |
| --- | --- | --- | --- |
| 1. 빠른 E2E | `npm run e2e` — 가짜 렌더러·가짜 Claude·가짜 Meta로 띄운 시험 서버에 휴대폰(390px)·PC(1280px) 화면으로 전체 흐름 | 모든 push·PR (GitHub Actions `e2e` 작업), 배포 전 | 2~4분 |
| 2. 실제 서버 점검 | `npm run e2e:live` — 배포된 주소에 읽기만 하는 점검 (계정·데이터를 바꾸지 않음) | 배포가 끝난 직후 (배포 작업 마지막 단계) | 30초 |
| 3. 실제 렌더 | `npm run e2e:render` — 진짜 Remotion 렌더(목소리 없음)로 영상 1개를 끝까지 만들고 자동 품질 검사·카드·표지 파일 확인 | 영상 패키지를 바꾼 뒤 수동, 큰 배포 전 | 10~30분 |

## 3. 시험 환경 (1단계)

- 시험 서버: `apps/studio/e2e/server.ts` — 진짜 서버(`startServer`)와 같은 코드에 바깥 연결만 바꿔 끼운다.
  - 렌더러: 작은 영상·그림 파일을 쓰는 가짜 (`runRender`의 나머지 — 진행 단계, 품질 검사 기록, 카드 묶음, 표지 JPEG — 는 진짜 코드)
  - 품질 검사: 기본은 통과. 시나리오에서 "다음 렌더는 대사 잘림" 같은 결과를 시험용 API로 정할 수 있다.
  - Claude(레시피 읽기·주제 더 보기·윤문): 정해진 답을 주는 가짜
  - Meta(인스타그램): 가짜 (게시는 바깥으로 나가지 않음)
  - 목소리: `TTS_PROVIDER=none`
  - 데이터 폴더: 실행마다 새 임시 폴더 (숨은 폴더 안 — 경로 문제도 함께 확인)
  - 시험용 API(`/__e2e/*`)는 이 시험 서버에만 있다. 운영 서버 코드에는 없다.
- 클라우드처럼 보이게: `TRUST_PROXY=1`, 화면 요청에 `X-Forwarded-For`를 붙여 "이 PC 전용" 모드가 아닌 로그인 모드로 시험한다. `STUDIO_SETUP_CODE`로 화면에서 첫 계정을 만든다.
- 브라우저: Playwright Chromium. 프로젝트 2개 — `mobile`(390×844, 터치), `desktop`(1280×800).

## 4. 시나리오와 합격 기준

모든 시나리오 공통: 화면 오류(pageerror) 0개, 휴대폰에서 가로 넘침 0px.

### A. 계정·로그인 (`accounts.spec.ts`)

| # | 시나리오 | 합격 기준 |
| --- | --- | --- |
| A1 | 설정 코드로 첫 계정(연구자 체크) 만들기 | 틀린 코드는 오류 문구, 맞으면 콘텐츠 목록. `/api/auth/me`의 role = researcher |
| A2 | 로그아웃 → 틀린 비밀번호 → 맞는 비밀번호 | 틀리면 "맞지 않아요", 맞으면 들어감 |
| A3 | [계정]에서 도우미 계정 추가 → 도우미로 로그인 | 목록에 보임. 도우미 화면에는 "계정 추가는 연구자 계정만" |
| A4 | 도우미가 승인 시도 | 승인 거절 문구("연구자 계정만"), 승인 기록 없음 |
| A5 | 비밀번호를 잊었어요 → 설정 코드로 재설정 | 새 비밀번호로 로그인됨, 옛 세션은 끊김 |
| A6 | 내 비밀번호 바꾸기 | 지금 비밀번호가 틀리면 거절, 바꾸면 이 기기는 계속 로그인 |

### B. 콘텐츠 전체 흐름 (`flow.spec.ts`, 연구자 계정)

| # | 시나리오 | 합격 기준 |
| --- | --- | --- |
| B1 | 새 콘텐츠: 예시 레시피(호두정과)로 만들기 | 대본 단계로 이동 |
| B2 | 후보 5개 → [다른 후보 보기] → 하나로 만들기 | 첫 대사가 서로 다른 후보 5개, 다시 보기에 같은 조합 없음. 고른 후보의 첫 대사가 최신 대본 |
| B3 | 영상 만들기 진행 → 완료 | 진행 표시가 끝까지 감, 품질 검사 패널 "통과", 영상·표지·레시피 카드 파일 열림 |
| B4 | 블로그 원고 2개 비교 → 하나 고르기 | 고른 유형이 서버에 저장됨 |
| B5 | 승인 전 내보내기·게시 기록 | ZIP 409, 게시 기록 버튼 막힘 |
| B6 | 검수 체크 → 승인 | ZIP 200, ZIP 안 블로그에 "조리기능장 이희재" 검토 문구(연구자 승인), 재료·분량이 원본과 같음 |
| B7 | 게시 기록 → 같은 콘텐츠 다시 기록 | 두 번째는 "다시 기록할까요?" 확인창 → 확인하면 기록됨 |
| B8 | 연구자 답변 없이 네이버 발행 기록 | 막힘("답변 대기"). 답변 입력 뒤 기록됨, 블로그에 답변 원문 그대로 |
| B9 | 승인 뒤 대본 고치기 | 새 버전, 상태 검수 대기, 옛 영상 ZIP 409 (원칙 2) |

## 5. 실패했을 때

- 1단계는 실패하면 GitHub Actions에 Playwright 보고서(화면 사진·동영상·trace)를 올린다. 배포 작업은 E2E가 통과해야 시작한다.
- 2단계가 실패하면 배포 작업이 빨간색으로 끝난다 (이미 배포된 뒤이므로 바로 고치거나 이전 커밋으로 되돌린다).
- 같은 시험이 가끔만 실패하면 재시도로 덮지 않고 원인을 고친다 (`retries`는 CI에서 1번만, 재시도로 통과하면 보고서에 "flaky"로 남음).

### E2E가 찾은 것

| 무엇 | 어떻게 고침 |
| --- | --- |
| 보안 헤더(`nosniff`)가 미디어 파일에만 붙고 다른 응답에는 없음 (실제 서버 점검 F4) | 모든 응답에 `nosniff`·`X-Frame-Options: DENY`·`Referrer-Policy` (단위 시험 추가) |
| 응답 JSON에 서버 데이터 폴더 절대 경로(`outputDir`)가 들어 있음 (D6) | 응답에서 뺌 (단위 시험 추가) |
| 데이터 폴더가 숨은 폴더(`.`으로 시작) 안에 있으면 ZIP 내려받기가 404 | 서버가 정한 파일은 그대로 보냄, 단위 시험 데이터 폴더를 숨은 폴더 안으로 |
